# SCD Type 2 — History Rows

Type 2 adds a new row each time a tracked attribute changes, so every
point-in-time question ("what was their region when they ordered?") has an
exact answer. It costs row growth — apply it per attribute, only where
point-in-time truth is genuinely needed. For overwrite-only attributes use
[SCD1.md](./SCD1.md).

Examples are portable SQL with ANSI type names; map them to your engine's.

## Shape

```sql
CREATE TABLE dim_customer_hst (
    customer_sk    BIGINT GENERATED BY DEFAULT AS IDENTITY,  -- surrogate, unique per version
    customer_bk    VARCHAR   NOT NULL,                       -- durable business key
    customer_name  VARCHAR,
    region         VARCHAR,
    valid_from     TIMESTAMP NOT NULL,
    valid_to       TIMESTAMP NOT NULL DEFAULT TIMESTAMP '9999-12-31 00:00:00',
    is_current     BOOLEAN   NOT NULL DEFAULT TRUE,
    row_hash       VARCHAR,                                  -- change-detection hash
    load_ts        TIMESTAMP DEFAULT CURRENT_TIMESTAMP       -- audit only, never validity
);
```

Store validity in one agreed time zone (UTC), in a timestamp type without a
zone, so two loads can't disagree about the same instant.

### Interval convention

Use **left-closed / right-open** intervals — `valid_from <= t < valid_to` —
so every instant maps to exactly one version with no overlap and no gap. Use
a high sentinel (`9999-12-31`) for the open end **and** an explicit
`is_current` flag (don't rely on one alone).

## Change detection — hash, null-safe

Build a `row_hash` over the tracked columns, coalescing NULLs to a sentinel
so `NULL` and `''` don't collide, with a delimiter between values:

```sql
MD5(
       COALESCE(CAST(customer_name AS VARCHAR), '^^NULL^^')
    || '|' || COALESCE(CAST(region AS VARCHAR), '^^NULL^^')
) AS row_hash
```

Use your engine's hash function (`MD5` is enough for change detection). Don't
swap the `COALESCE`s for `CONCAT_WS`: it skips NULLs, so `('A', NULL, 'B')`
and `('A', 'B', NULL)` hash the same.

What goes into the hash:

* **The tracked business attributes only** — never keys, load timestamps,
  batch IDs, or other metadata, or every reload looks like a change.
* **In one fixed, documented column order** (alphabetical is a fine
  convention). The fixed order makes the hash reproducible; it doesn't make
  it survive schema change. Adding or removing a hashed column changes every
  row's hash, so treat it as a change to the dimension: rehash history in a
  heal ([BACKFILLING.md](./BACKFILLING.md)) in the same release, or the next
  load sees every row as changed.

Compare incoming `row_hash` to the current row's; differ → close the old, open
the new.

## Load — close-and-insert

Take validity from the **source, never the load clock**: `valid_from` is when
the change happened (the source's change timestamp, or the snapshot date for a
snapshot source). Validity stamped with `CURRENT_TIMESTAMP` depends on when
the job ran, so it can never be reproduced — the same flaw that rules out
snapshot features below. The load's own time goes only in `load_ts`.

Before loading, reduce the batch to **one row per key** — the latest change,
with timestamp ties broken by a deterministic source sequence (log position,
ingest offset) — or apply the batch's changes in order. Otherwise the `MERGE`
fails or opens two current rows. A **back-dated** change (older than the
current row's `valid_from`) can't be placed by close-and-insert: route that
key to a heal ([BACKFILLING.md](./BACKFILLING.md)).

A single `MERGE` can't both update the expiring row and insert the new one for
the same key, so the portable pattern is two statements: (1) **close** changed
current rows, (2) **insert** the new versions. Run them in one transaction
where your engine supports it.

```sql
-- stg_customer: one row per customer_bk, with changed_at taken from the source
-- Step 1: close current rows whose hash changed
MERGE INTO dim_customer_hst tgt
USING (SELECT s.*, <row_hash expr> AS row_hash FROM stg_customer s) src
   ON  tgt.customer_bk = src.customer_bk
   AND tgt.is_current = TRUE
WHEN MATCHED AND tgt.row_hash IS DISTINCT FROM src.row_hash THEN
   UPDATE SET valid_to   = src.changed_at,   -- closes exactly where the new version opens
              is_current = FALSE;

-- Step 2: insert a version for every key with no current row
--         (brand-new keys, and the keys step 1 just closed)
INSERT INTO dim_customer_hst
   (customer_bk, customer_name, region, valid_from, valid_to, is_current, row_hash)
SELECT src.customer_bk, src.customer_name, src.region,
       src.changed_at, TIMESTAMP '9999-12-31 00:00:00', TRUE, src.row_hash
FROM (SELECT s.*, <row_hash expr> AS row_hash FROM stg_customer s) src
LEFT JOIN dim_customer_hst cur
       ON cur.customer_bk = src.customer_bk AND cur.is_current = TRUE
WHERE cur.customer_bk IS NULL;
```

Step 2 only inserts where no current row exists, so the pair is safe to
re-run: if step 2 fails after step 1, running both again inserts the missing
versions, and a second full run changes nothing.

## Don't rely on snapshot features

Don't use a transform tool's built-in snapshot feature (dbt `snapshot`, for
example) for an SCD2 you need to trust. A snapshot records only the state it
happens to observe on each run, so its history is path-dependent — a missed
or late run is a permanent gap, its state is opaque, and a logic fix can't be
replayed over the past. Implement the close-and-insert pattern above as a
reusable macro or model inside the transform project instead, so the SCD2
logic is version-controlled, testable, and reviewed like any other
transformation. For a clean rebuild from full history, use the Healing-Table
approach in [BACKFILLING.md](./BACKFILLING.md).

## Validate after every load (block on failure)

* Exactly **one current row** per durable key — count over *all* rows, so a key
  with no current row is caught too
  (`GROUP BY customer_bk HAVING SUM(CASE WHEN is_current THEN 1 ELSE 0 END) <> 1`
  → empty).
* The current flag agrees with the high date
  (`is_current` exactly when `valid_to = '9999-12-31'`).
* `(customer_bk, valid_from)` is unique.
* **No overlapping** intervals per key (`LEAD(valid_from)` ≥ `valid_to`).
* **No gaps** if continuity is required.
* `valid_from < valid_to` on every row.
* No **consecutive duplicate** versions — same hash **and** contiguous
  (`valid_from` = the previous `valid_to`). Same-hash rows with a gap between
  them are separate states, not duplicates.

## Querying point-in-time

```sql
SELECT * FROM dim_customer_hst
WHERE customer_bk = :bk
  AND :as_of_ts >= valid_from
  AND :as_of_ts <  valid_to;
```

Carry the **durable key** on facts alongside the surrogate so you can also
report all history by *current* attributes. An SCD2 dimension holds all three
key types at once — the surrogate (one per version, the FK target), the
natural/business key (lineage), and the durable "super-natural" key (joins all
versions of one entity). See [KEYS.md](./KEYS.md) for the full rules.
